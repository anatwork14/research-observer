# Graph and timeline UI contract

This directory renders derived research-evolution views. Read `docs/RESEARCH_EVOLUTION.md` before changing graph/timeline behavior, `docs/MANUSCRIPT_CLAIMS.md` before changing explicit manuscript Claim behavior, `docs/CLAIM_EVIDENCE_RELATIONS.md` before changing authored Claim↔Evidence semantics, and `docs/CLAIM_EVIDENCE_REVISION_HISTORY.md` before changing historical Claim/Evidence comparison.

- Keep the existing force-directed **Research graph** available. Provenance and Timeline are complementary views, not replacements.
- Project scope comes from the selected stable research project ID and must be preserved in graph-view/filter navigation.
- Provenance edges are visualizations of already-resolved source, semantic, citation, passage-location, explicit-claim, authored Claim↔Evidence, or revision relationships. The UI must not manufacture missing semantic edges.
- Manuscript Passage nodes are literal saved `.tex` blocks around citation occurrences and/or explicit Claim anchors. They may display file/line/section and a bounded literal excerpt, but must never be relabeled or interpreted as semantic claims.
- Explicit manuscript Claim nodes exist only when the author writes a valid unique `% observaire:claim <id>` marker in saved visible editable `.tex` source.
- Claim nodes must remain visually and semantically distinct from canonical research nodes whose role happens to be `claim`.
- Claim structure may show only `Passage → anchors_claim → Claim → part_of → Manuscript` unless a valid explicit Claim↔Evidence directive separately authorizes a semantic edge.
- Authored Claim↔Evidence edges exist only for strict `% observaire:claim-evidence <claim-id> <relation> <evidence-slug>` directives whose Claim and canonical same-project `type:evidence` target both validate in the live projection.
- Keep the authored Claim↔Evidence graph layer independently toggleable from canonical research semantics, citations, and Claim structure.
- Never infer Claim↔Evidence meaning from citation proximity, prose wording, annotation type, AI interpretation, or graph distance.
- Duplicate, invalid, orphan, malformed, unresolved, cross-project, and non-Evidence endpoints stay visible as health issues; do not guess or auto-correct them.
- Multiple citations in the same saved passage may share one Passage node. Citation and Claim layers referring to the same block must converge on the same Passage identity.
- Ambiguous/missing citation keys must remain visibly unresolved rather than being attached to a guessed research object. They may still expose literal saved-source location context.
- Semantic version lineages come only from explicit same-project `supersedes` edges. Display direction is oldest→newest even though stored edge direction is newer→older.
- Manuscript revision events come only from actual Git commits. Dirty working files are not revision events.
- Historical Claim/Evidence snapshots live only in **Timeline & versions** in the first implementation. Research Graph and Provenance must not load historical Claim snapshots merely to render.
- Historical Claim snapshots use committed `.tex` bytes plus the committed manuscript visibility state for that revision. Current dirty editor state must remain visibly separate.
- A historical Claim↔Evidence directive proves what the manuscript explicitly authored at that commit. Endpoint validation must not decide whether the authored directive existed.
- For selected Base/Compare snapshots, historical Evidence endpoint status is resolved from canonical research state at the **same Git commit** using exact canonical slug, exact selected project identity, and exact `type: evidence`.
- Historical endpoint statuses may be valid, missing, ambiguous, cross-project, wrong-type, or unavailable. Incomplete bounded historical research scans must yield unavailable rather than a guessed valid/missing state.
- Current canonical Evidence state is a separate present-day annotation. A current `/progress/<slug>` navigation link is allowed only when the selected historical endpoint was valid same-project Evidence and the slug is current canonical Evidence today.
- Historical endpoint indexing is limited to the selected Base/Compare revisions that contain authored Evidence links; do not scan all historical revisions merely to render Timeline chronology.
- Raw `claimBase`/`claimCompare` query values must first resolve against the already-loaded snapshot set. Never pass arbitrary query values directly to Git for manuscript or historical research reads.
- Historical Claim identity is exact authored Claim ID. Do not infer Claim renames from similar prose or adjacent revisions.
- A `relation-changed` event is valid only for an unambiguous one-old/one-new relation change on the same exact Claim/Evidence endpoints. Ambiguous many-to-many changes remain additions/removals.
- Historical comparison/filter state remains URL-backed with `claimBase`, `claimCompare`, `claimHistory`, `evidenceHistory`, `historyEvent`, `historyRelation`, and comparison presentation mode `historyChanged=only`. These parameters operate over already-loaded snapshots and must not create hidden client history state.
- `evidenceHistory` is an exact authored Evidence-slug focus, not a canonical lookup. It may filter chronology, matrix, and side-by-side authored state before historical endpoint validation, but must never upgrade a slug to historically valid Evidence by itself.
- `historyEvent` may use only one exact explicit historical event type already emitted by the history service. Unsupported values normalize to no event filter; do not alias or infer event categories.
- `historyRelation` may use only `supports`, `contradicts`, `contextualizes`, or `qualifies`. It may match explicit snapshot link relation values or exact event `relation` / `beforeRelation` / `afterRelation` fields only. Never derive a relation filter match from prose, citation content, endpoint status, or current canonical metadata.
- Claim, Evidence, event, and relation history filters combine with strict AND semantics. A focused Claim must still satisfy every other active filter. Evidence focus may include only explicit events carrying that exact `evidenceSlug`; Claim-text/move/add/remove events without an Evidence endpoint do not become Evidence events. A relation filter similarly excludes event types that carry no matching explicit relation field.
- When an event-type filter is active, unfocused matrix and Base→Compare Claim rows must come from events matching every active filter. Snapshot relation/Evidence membership must not widen an event-filtered result set.
- Invalid Claim/Evidence/event/relation filter values normalize to no corresponding filter. Never fuzzy-match historical focus by title, DOI, citation key, alias, prose, or substring.
- `historyChanged=only` is a Base→Compare **presentation mode**, not a new semantic event type. A Claim is “changed” only when at least one already-emitted explicit comparison event survives the active Claim/Evidence/Event/Relation filters. Added and removed Claims therefore count as changed through their explicit events. Never infer changed/unchanged from prose similarity, line distance, timestamps, or current canonical metadata.
- With the default All matching mode, bounded side-by-side rows may include matching snapshot state that has no matching explicit comparison event. Such rows must collapse by default with native disclosure controls. Claims with matching explicit changes are ordered ahead of unchanged matching rows so the 20-row bound does not bury explicit additions/removals/changes.
- Changed-only mode applies only to the Base→Compare Claim row list. It must be preserved by URLs/form/navigation but must not filter chronology, the 12-revision matrix, or expand historical research indexing.
- Matrix and chronology drill-down links must preserve selected project, Base/Compare pair, comparison mode, and the other active filters through URLs. Filter-removal controls must remove only their named semantic dimension unless the user explicitly chooses Clear filters; Clear filters should preserve the comparison presentation mode.
- Base/Compare authored Evidence cards may expose a separate Evidence-history focus action even when the historical endpoint is missing, wrong-type, cross-project, ambiguous, or unavailable. That action filters literal authored history and must remain separate from current canonical `/progress/<slug>` navigation.
- The multi-revision Claim matrix is a bounded view over already-loaded manuscript snapshots (latest 12 snapshots × at most 20 Claim rows). It must remain inside its own horizontal scroller, keep Claim identity readable while scrolling, and must not trigger historical research indexing for matrix-only revisions.
- The Base→Compare event summary is derived only from the existing explicit comparison event stream. Its relation-transition matrix may count only conservative `relation-changed` events; it must not pair `relation-added`/`relation-removed` events heuristically.
- Event-count summary pills may set only the existing exact `historyEvent` filter, and relation labels in the transition matrix may set only the existing exact `historyRelation` filter. They must preserve every other active filter and the selected Base/Compare pair. Numeric relation-transition cells remain non-interactive factual counts; do not invent a pairwise `historyTransition` query or imply that an ambiguous relation pair exists.
- Base/Compare stepping and swap controls operate only on the already-loaded snapshot sequence. “Older” and “Newer” mean adjacent positions in Git snapshot order, never displayed timestamp order. Edge controls must disable instead of wrapping or discovering revisions outside the bounded history window, and every active Claim/Evidence/event/relation filter plus comparison mode must survive a pair-navigation click.
- Do not deep-link historical Claim line numbers into the current IDE as if those lines necessarily still existed.
- Timeline chronology uses explicit note dates, validated experiment-run timestamps, and Git commit timestamps only. Historical Claim snapshot adjacency follows Git history order; displayed commit timestamps do not reorder it. Date-only research metadata must remain the same calendar day in every viewer timezone.
- The version comparison panel compares explicit supersedes pairs only and must expose truncation when a bounded diff does not include the complete note bodies.
- Local PDF sources and stored external scholarly/Consensus sources may appear in the source lane, but the latter must come only from canonical verified identifiers already persisted with evidence.
- Passage/Citation/Claim `Open manuscript location` links must use the IDE's validated file/line navigation; hidden, missing, resource, unrelated-project, or otherwise invalid files must not be opened through provenance navigation.
- Wide provenance SVG content must scroll inside its graph container. Never let it force document-level horizontal overflow on mobile/tablet.
- Large provenance projections render a bounded working set (currently 90 nodes per lane). Search and selected-trace nodes receive priority. Do not silently imply that the bounded canvas is the complete underlying projection.
- Selecting a provenance node traces the enabled visible relationship graph up to seven hops so a paper/evidence/citation/passage/claim/manuscript/revision chain can be followed as one focus path. Layer toggles must change that trace rather than bypassing disabled layers.
- Interactive graph controls require keyboard access and visible focus. Touch/tablet remains first-class.
- Optional manuscript/citation/claim/Git/historical-research layers must fail soft. A missing optional scan must not take down the canonical research graph, and an unavailable scan must not be displayed as a factual zero.

After changing this surface, verify all three `/graph` views at desktop, tablet portrait/landscape, and narrow mobile widths in addition to the focused evolution tests, historical Evidence resolver tests, and `npm run verify:merge-local`.
